# 설계: 경험 지도와 프로필 연대기

> 작성: Claude (2026-11-05) · 상태: **사람 확정 (2026-11-05), 구현 전** · 관련 항목: F-010, F-011, F-203

## 이 문서를 언제 쓰는가

자료 분류, 본인·타인 구분, 경험 단위, 프로필, 연대기, 성장 서사, 자소서 매칭을 설계하거나 고칠 때 읽는다.

## 1. 목적

사용자는 드라이브를 정리하지 않고 올린다. 실제 계정(2026-11-05)은 폴더 346개, 읽힌 파일 512개이고, 이름에 연도가 있는 파일은 32개뿐이다. 다른 사람의 자소서도 같은 폴더에 있다. 폴더만으로는 경험과 시기, 소유를 알 수 없다. 그래서 파일을 읽어 경험 단위로 재구성하고, 사람이 확인한 내용만 프로필과 자소서에 쓴다.

## 2. 단위

| 단위 | 뜻 | 예 |
|---|---|---|
| 파일 | 올린 원본 하나 | 보고서, 코드, 이력서 |
| 경험 | 목표가 하나이고 시작과 끝이 있는 일. 프로젝트 요약의 단위이자 연대기의 막대 하나 | 화력발전소 이상탐지, 인턴십, 공모전 |
| 이력 | 경험이 속한 소속과 공식 기록 | 학교, 군, 회사, 자격증, 수상, 어학 |
| 역량 | 여러 경험에 걸쳐 쌓인 기술과 주제 | 시계열 분석, Python |

폴더는 경험의 단서일 뿐이다. 한 폴더에 경험이 여럿일 수 있고 한 경험이 여러 폴더에 걸칠 수 있다. 수업 자료 묶음은 과목 하나를 경험 하나로 본다.

## 3. 단계별 읽기

파일 추출은 CPU만 쓰고, 모델에 넘길 때 토큰이 든다. 학생 폴더에는 JSON, 로그, 코드처럼 사람이 쓴 글이 아닌 파일이 훨씬 많으므로 전부 모델에 넘기지 않는다. 기준은 `skive/drive_tiers.py`다.

| 단계 | 대상 | 처리 | 모델 |
|---|---|---|---|
| 0 구조 | 전체 파일 | 이름, 폴더, 형식, 날짜. 시스템 파일과 잠금 파일은 제외 | 없음 |
| 1 문서 | PDF, DOCX, PPTX, MD, TXT, HWP | 먼저 추출하고 끝까지 읽는다 | 있음 |
| 2 결과 | XLSX, 노트북, 이름이 결과·보고·README인 파일 | 첫 구간만 본다 | 있음 |
| 3 원시 | 코드, CSV, JSON, 로그 | 문서가 없을 때 대표 몇 개의 첫 구간만 본다. 그 외에는 문서가 언급하거나 사용자가 물을 때 검색으로 찾는다 | 필요할 때 |

활동 하나의 모델 입력은 약 120만 자로 제한하고, 넘으면 읽은 범위를 숫자로 표시한다.

## 3.1 처리 순서

1. **파일 카드**: 파일마다 문서 유형, 한 줄 내용, 핵심어, 등장 인물, 날짜 단서를 만든다. 모델 입력은 첫 구간만이 아니라 제목·표·결론 등 대표 구간이다.
2. **소유 판별**: 본인, 팀, 타인, 참고자료, 불명으로 나눈다. 단서는 프로필 이름과 문서 안 이름, 문서 작성자 속성, 드라이브 소유자, 폴더명("선배", 타인 이름)이다.
3. **시기 추정**: 문서 안 날짜 → 파일·폴더 이름(`25-2`, `26년하반기`) → 파일 생성·수정일 순으로 쓰고 신뢰도를 남긴다. 일괄 업로드 날짜는 활동 시기로 쓰지 않는다.
4. **경험 묶기**: 카드 전체를 모델이 한 번에 보고 경험 후보, 대분류, 소분류, 파일 연결을 제안한다. 폴더, 시기, 공통 핵심어, 인물이 근거다. 한 파일이 여러 경험에 속할 수 있다.
5. **사람 확인**: §5 순서로 확인한다.
6. **경험 요약**: 경험마다 기존 프로젝트 요약 틀로 MD를 만든다.
7. **프로필 조립**: 이력, 경험 막대, 역량 흐름, 성장 서사를 만든다.

대분류는 고정한다: 학교 수업, 프로젝트, 대외활동·공모전, 인턴·직장, 연구, 취업 준비, 참고자료. 소분류는 학기, 과목, 회사처럼 자동으로 만든다.

## 4. 불변조건과의 관계

- 드라이브 화면의 폴더와 파일명은 바꾸지 않는다. 분류는 `내 경험`의 별도 보기다 (불변조건 5).
- 타인 자료는 기본적으로 경험과 자소서 근거에서 제외한다. 사용자가 지정하면 표현 참고로만 쓴다 (불변조건 2).
- 서사는 `derived`다. 확인된 사실에서만 만들고 문장마다 근거 경험을 연결한다 (불변조건 1, 7).
- 추정 시기는 추정으로 표시한다. 사용자가 확인하기 전에는 확정 표기하지 않는다.

## 5. 사람 확인 순서

질문을 한꺼번에 내지 않는다.

1. **프로필 기본값**: 이름과 학교를 먼저 받는다. 이력서가 있으면 후보를 채운다. 이름은 소유 판별의 기준이다.
2. **경험 지도 확인**: 경험 후보 카드를 보고 맞음, 합치기, 나누기, 타인 자료, 제외를 고른다.
3. **경험별 역할 질문**: 자소서에 쓸 경험부터 1~3개만 묻는다. 답은 `user_statement`다.

## 6. 프로필과 자소서 연결

프로필은 연대기(막대), 이력 카드, 프로젝트, 자격증, 어학, 수상, 역량 흐름, 성장 서사로 구성한다. 자소서는 문항에서 필요한 역량을 뽑고, 그 역량이 있는 확인된 경험을 고른 뒤 확인된 사실로 쓴다. 성장 서사는 경험 선택과 흐름 구성에만 쓰고, 사실 근거로는 쓰지 않는다.

## 7. 완료 조건 (승인 후 항목으로 분리)

- [ ] (real_data) 실제 계정에서 타인 폴더 파일이 본인 경험에 연결되지 않는다
- [ ] (real_data) 드라이브 구조를 바꾸지 않고 경험 후보가 만들어진다
- [ ] (manual) 프로필에 확인된 경험만 연대기로 표시되고, 추정 시기가 구분된다
- [ ] (real_data) 자소서 초안이 타인 자료의 내용을 근거로 쓰지 않는다
- [ ] (deterministic) 사용자가 제외한 경험의 사실은 검색과 자소서에 나오지 않는다

## 7.1 첫 실험 결과 (2026-11-05, 실제 계정 읽기 전용, 파일 512개)

- 파일 카드: 512개 전부 생성. 본인 186, 타인 128, 불명 108, 참고 59, 팀 31.
- 타인 판별: `선배님들 자소서` 131개 중 타인 104, 참고 23, 본인·팀 3, 불명 1. 폴더 단서를 규칙으로 함께 써야 한다.
- 경험 묶기: Haiku로 27개 후보. 입력 약 5.9만, 출력 약 1만 토큰.
- 결함: 모델이 입력에 없는 파일 번호를 돌려 타인 파일 24건이 경험에 연결됐다. 서버는 입력한 번호만 받아들이고, 타인 파일은 코드로 제외해야 한다.
- 결함: 같은 일이 여러 경험으로 쪼개진 사례가 있다(한 회사 과제가 4개로 분리). 사용자 합치기 화면이 필수이고, Sonnet 비교가 필요하다.

## 8. 열린 질문

- 이미지와 스캔 문서만 있는 경험의 처리.
