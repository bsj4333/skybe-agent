## 1. 무엇을 요약하는가

드라이브의 **폴더는 보관 위치**이고, 사용자가 나중에 묻는 단위는 **활동**이다. 활동은 팀 프로젝트,
개인 프로젝트, 전공 수업, 연구, 실험, 동아리, 인턴, 공부 기록 등이 될 수 있다. 하나의 폴더에 여러
활동이 있을 수 있고, 하나의 활동을 설명하는 파일이 여러 폴더에 흩어질 수도 있다. 같은 파일이 수업과
그 수업의 팀 프로젝트 양쪽을 설명할 수도 있다.

따라서 `폴더 1개 = 경험 1개`로 저장하지 않는다. 폴더 요약은 **무엇이 들어 있는지 보여 주는 목차**로,
활동 요약은 **사용자가 실제로 한 일·배운 일의 검토 가능한 기록**으로 구분한다.

### 현재 구현과 차이

- 현재 `skive/drive_summary.py`는 한 폴더의 분석 가능 파일 중 우선순위가 높은 최대 24개를 고르고,
  각 파일의 앞쪽 청크 최대 3개와 전체 100,000자만 사용해 최대 12개 문장을 만든다. 이 초안은 선택된
  자료의 발췌다. 전체 폴더·사용자 이력을 이해한 결과가 아니다.
- 인용의 **원문 존재·문장 겹침·수치·주체 충돌**을 자동 검사하지만, 인용이 주장 전체를 충분히
  뒷받침하는지, 최신본인지, 실제 본인 기여인지는 확인하지 못한다.
- 현재 초안의 `facts`는 별도 `drive_folder_summaries` JSON에 있고, 계정별 활동·사실·자소서 저장소와
  이어지지 않는다. `migrations/0001_init.sql`의 `experiences`는 학년 필수, 제한된 활동 유형,
  폴더에 가까운 `slug`, 사실의 `verified` 불리언을 전제로 한다. 다양한 수업·활동과
  [SCHEMA.md](SCHEMA.md)의 v2 사실 상태를 담으려면 후속 마이그레이션이 필요하다.

## 2. 공통 구조: 빈칸을 허용하는 활동 카드

모든 전공에 같은 기술 지표나 같은 성과 형식을 요구하지 않는다. 공통 질문은 아래처럼 작게 유지하고,
답이 없는 항목은 추측해서 채우지 않는다.

| 공통 질문 | 수업 예시 | 팀·개인 프로젝트 예시 |
| --- | --- | --- |
| 무엇을 다뤘나? | SCM 수업의 BOM·CAPA | 이상탐지 문제와 대상 설비 |
| 왜 했나? | 강의·과제의 학습 목표 | 해결하려는 문제와 제약 |
| 무엇을 했나? | 학습·실습·과제 | 설계·실험·구현·분석·의사결정 |
| 누가 했나? | 개인 과제인지 팀 과제인지 | 사용자·팀·다른 사람 중 누구의 행동인지 |
| 무엇이 나왔나? | 이해한 개념·제출물·남은 의문 | 산출물·측정 결과·실패·한계 |
| 근거와 빈칸은? | 강의자료 위치·사용자 진술 | 보고서 위치·측정 조건·본인 역할 확인 질문 |

활동 카드의 고정 필드는 `activity_id`, `user_id`, 제목, 선택적 기간·소속, 상태, 연결된 파일과
사실 ID 정도다. `course`, `team_project`, `personal_project`, `research`, `experiment` 같은 분류는
**검색용 태그**다. 자료가 수업이자 프로젝트라면 태그를 둘 다 붙일 수 있다. 모르면 `분류 미정`으로 둔다.
학년, 성과 수치, 본인 역할, 성장 이야기는 필수 입력이 아니다.

세부 내용은 활동 카드의 자유 서술만으로 보관하지 않고 **작은 사실 단위**로 기록한다. 사실의 종류는
`맥락`, `목표`, `개념`, `역할`, `행동`, `판단`, `산출물`, `측정 결과`, `배운 점`, `한계` 등이다.
전공별 용어는 별도 태그·속성으로 붙이고 공통 종류를 늘려만 가는 방식은 피한다. 예를 들어 화공
`반응 온도`, 기공 `하중 조건`, 전자 `샘플링 주파수`는 모두 측정 조건이며 원래 용어·단위를 그대로
보존한다. 수업의 개념 설명처럼 행위 주체가 없는 사실에는 주체를 억지로 `본인`이라고 붙이지 않는다.

## 3. 저장과 Markdown의 관계

```text
사용자별 원본 파일·버전
  → 파일별 읽기 기록·근거 위치
  → 활동 후보와 파일 연결(여러 파일 ↔ 여러 활동)
  → 출처·주체·상태가 있는 개별 사실
  → 활동별 Markdown / 폴더 목차 Markdown / 전체 이력 보기
  → 질문 답변·자소서·면접 준비
```

**Markdown은 사람이 읽고 고치는 화면이자 내보내기 형식**이다. 내용의 기준은 계정별 DB에 저장한
파일 버전, 사실 버전, 인용, 사용자 확인이다. 같은 데이터에서 Markdown을 다시 생성해야 파일 변경과
정정 후에도 두 저장소가 어긋나지 않는다. 사용자가 Markdown 문장을 수정하면 원문 사실을 덮어쓰는
대신 `사용자 진술/정정 제안`으로 받아 확인 후 새 버전을 만든다.

활동마다 생성된 MD의 내용·버전·생성 시각을 `파생 결과물`로 저장하고, 화면에서 미리보기와 `.md`
다운로드를 제공한다. 드라이브에는 `생성된 정리본`으로 원본과 구별해 보여 줄 수 있다. 활동은 여러
폴더의 파일을 참조할 수 있으므로 MD를 어느 한 원본 폴더의 유일한 사실 파일로 취급하지 않는다.
파일이나 사실이 바뀌면 기존 다운로드 버전은 보존하되 화면에서 `이전 버전`으로 표시한다.

### 최소한의 연결 정보

| 기록 | 꼭 필요한 정보 |
| --- | --- |
| 파일 읽기 기록 | `user_id`, 파일 ID·버전·해시, 파서 버전, 처리 상태, 페이지/시트/행 등 읽은 범위, 읽지 못한 이유 |
| 활동 | `user_id`, 안정적인 활동 ID, 제목·태그, 관련 파일 ID들, 병합·분리 이력, 검토 상태 |
| 사실 | 활동 ID, 종류, 문장, 주체(`본인/팀/타인/불명/해당 없음`), 출처 유형(`문서/사용자 진술/AI 해석`), 검토·유효 상태, 버전 |
| 근거 | 파일 ID·**버전**, 안정적인 청크 ID, 페이지/슬라이드/셀/행 위치, 원문 인용, 인용 존재 검사와 의미상 지지 판단을 각각 기록 |
| 수치 | 지표 이름, 값, 단위, 비교 기준, 측정 조건·기간, 주체; 빠진 값은 `미확인` |
| 생성된 MD | 생성 시 사용한 파일·사실 버전, 분석 범위, 모델·프롬프트 버전, 생성 시각, 갱신 필요 여부 |

기존 `SCHEMA.md`의 `provenance_type`, `evidence_status`, `review_state`, `lifecycle`과 사실
버전화 규칙을 그대로 이어간다. 단, 현재 SQL의 `verified` 한 칸과 `grade not null`, 제한된 `kind`,
행동 주체 2종은 이 구조를 표현하지 못하므로 **기존 테이블을 곧바로 재사용하거나 운영 데이터를
삭제하지 말고** 별도 마이그레이션을 설계한다. Supabase Auth 사용자 ID와 모든 읽기·쓰기 범위도
같은 `user_id`로 묶는다.

## 4. 큰 폴더를 읽는 순서

1. **목록 만들기:** 업로드된 원본을 파일별로 기록한다. 중복 해시, 비슷한 이름의 버전, 파일 유형,
   용량, 읽기 실패를 표시한다. `보관됨`과 `내용을 읽음`은 다른 상태다.
2. **파일별 읽기:** 보고서·강의자료·코드·표·원시 데이터에서 위치가 있는 작은 메모와 사실 후보를
   만든다. 긴 파일은 전체 구간을 여러 작업으로 처리한다. 대형 표는 가능한 범위에서 전체 행을
   프로그램으로 집계하고, 모델에는 집계·열 구조·대표 행과 검증 가능한 위치를 보낸다.
   이미지·스캔·영상은 별도 추출 작업이 없으면 `미분석`으로 남긴다.
3. **활동 찾기:** 파일 제목뿐 아니라 내용·기간·참조 관계로 같은 활동 후보를 묶는다. 서로 다른
   프로젝트를 한 폴더에 넣었다고 합치지 않고, 여러 폴더의 동일 활동도 연결할 수 있게 한다.
   모호하면 사용자에게 `합치기/나누기/이름 바꾸기`를 보여 준다.
4. **사실 모으기:** 파일별 후보의 중복·구버전·상충하는 수치와 역할을 비교한다. 최신 파일처럼
   보인다는 이유만으로 과거 수치를 지우지 않는다. 측정 조건이 다르면 별도 결과로 남긴다.
5. **질문과 확인:** 문서가 말하는 팀 성과와 사용자가 직접 한 일을 분리한다. 역할·수치·배운 점이
   비어 있으면 적은 수의 구체적인 질문을 한다. 사용자의 답은 `사용자 진술`로 저장한다.
6. **MD 생성·갱신:** 확인된 사실과 보류 사실을 구분해 활동별 MD를 만든다. 원본/사실이 바뀌면
   영향받은 활동 MD와 이후 자소서·답변을 `갱신 필요`로 표시하고 다시 만든다.

한 번의 모델 호출에 들어가는 입력량은 제한할 수 있다. 그러나 그 제한을 **전체 분석의 종료 기준**으로
쓰지 않는다. 배치별 처리 결과를 합치고, 화면에는 `업로드 n개 / 텍스트 추출 n개 / 모델 검토 n개 /
활동에 연결 n개 / 검토 필요 n개`를 따로 보여 준다. 원시 데이터의 통계 집계와 모델의 의미 해석
범위도 구별한다.

## 5. 활동별 Markdown 초안 형식

섹션은 활동에 해당할 때만 채운다. 근거가 없는 `성장`, `본인 성과`, `성과 수치`를 빈 문장으로
지어내지 않는다. 아래 예시는 **가상의 예시**이며 실제 사용자 자료의 분석 결과가 아니다.

```md
# [활동명] — 자료 기반 초안

상태: 일부 자료 분석 · 사용자 검토 전
분류: 수업 / 팀 프로젝트 / 개인 프로젝트 / 분류 미정 중 해당 항목
기간: 확인되지 않음
범위: 파일 30개 중 텍스트 추출 24개, 활동 연결 8개, 이미지 6개 미분석

## 한눈에
- 이 활동에서 다룬 주제와 자료로 확인된 결과를 2~3문장으로 적는다.
- 본인 역할이 불명확하면 여기서도 단정하지 않는다.

## 맥락과 목표
- 무엇을 왜 했는지. [사실 ID → 파일 버전·위치·인용]

## 진행한 일과 판단
- 팀이 수행한 일: … [자료에서 확인]
- 내가 수행한 일: 확인되지 않음. [본인 역할 질문 대기]

## 결과·산출물
- 지표명 / 수치·단위 / 비교 기준 / 측정 조건 / 주체를 함께 적는다.
- 수치가 없더라도 설계안·실험 기록·제출물·실패와 한계를 적을 수 있다.

## 배운 점·다음에 활용할 내용
- 자료에 적힌 학습 내용과 사용자 본인의 회고를 구분한다.

## 확인할 질문
1. 보고서의 '팀이 구현했다' 중 직접 맡은 부분은 무엇인가요?
2. 서로 다른 보고서의 결과 수치는 조건이 다른 실험인가요?

## 근거와 분석 범위
- 문장별 원본 열기: 파일명, 버전, 페이지/셀/행, 짧은 원문 인용
- 읽지 못한 파일·구간, 구버전·상충 자료, 마지막 분석 시각
```

예를 들어 SCM **수업**이면 `BOM·CAPA를 어떤 자료에서 배웠는지`, 과제와 헷갈린 개념이 중심이
되고 성과 수치는 없어도 된다. **팀 설계 프로젝트**이면 해결 과제·설계 선택·팀 결과와 본인 역할을
나눠 적는다. **화공 실험**이면 온도·농도·반복 횟수 같은 조건 없이는 수치만 단독 인용하지 않는다.
**전자 개인 프로젝트**이면 회로·코드·시험 기록이 여러 폴더에 있어도 하나의 활동으로 연결할 수 있다.

폴더의 `index.md`는 활동 목록, 대표 자료, 중복/버전 후보, 읽기 진행률을 보여 주는 **목차**다.
활동별 MD와 혼동하지 않도록 이름과 상태를 분리한다. 사용자 전체 이력 MD는 승인된 여러 활동
카드의 요약이며, 그 자체를 새 사실의 근거로 재사용하지 않는다.

## 6. 사용자에게 보여 줄 판단 기준

- `자료에서 확인`: 원문에 대응하는 내용이 있고 출처를 열 수 있다. 현실의 사실성이나 본인 기여를
  시스템이 인증했다는 뜻은 아니다.
- `본인 확인`: 사용자가 직접 말하거나 수정한 내용이다. 문서에서 확인된 내용과 구분한다.
- `AI 해석`: 여러 사실에서 뽑은 역량·성장·강점 해석이다. 사용자가 거절·수정할 수 있고 독립 근거가
  되지 않는다.
- `확인 필요`: 주체 불명, 수치 조건 누락, 인용의 의미상 지지 부족, 구버전 충돌, 미분석 자료가 있다.

특히 `인용문이 실제로 존재함`과 `그 인용이 주장 전체를 지지함`은 다른 검사다. 자소서에 들어가는
본인 행동·성과는 주체와 의미상 근거 또는 분명한 사용자 진술을 확인한다. 모호한 질문에는 관련
활동 후보와 출처를 제시하고, 찾지 못한 정보는 만들어 답하지 않는다.

## 7. 구현 순서와 단계별 완료 기준

이 문서는 설계 기준이다. 3번의 계정별 활동 ID·파일 연결·수동 분리와 목차 MD는 구현했으며,
자동 후보 분류·병합 이력은 남았다. 처음에는 실제 KT 자료 일부와 가상의
수업·기공·화공·전자 자료를 섞은 작은 평가 묶음으로 구조가 통하는지 확인한다.

1. **형식과 평가 사례 고정:** 파일 1개가 여러 활동에 속하는 경우, 한 폴더에 2개 활동이 있는 경우,
   수업이라 성과 수치가 없는 경우, 팀 결과만 있고 본인 역할은 없는 경우, 상충하는 수치·구버전,
   이미지 미분석을 기대 결과와 함께 적는다.
2. **파일 읽기 기록과 범위 표시:** 파일별 상태·버전·읽은 위치를 DB에 남긴다. 24개 선택 제한이
   전체 완료로 보이지 않아야 하고, 실패 파일을 재처리해도 중복 사실이 생기지 않아야 한다.
3. **활동과 파일의 다대다 연결:** 폴더와 독립된 활동 ID를 만들고, 사용자 병합·분리 후에도 근거
   연결을 보존한다. 다른 계정 파일은 후보에도 나타나지 않아야 한다.
4. **사실·수치·주체·버전 저장:** [SCHEMA.md](SCHEMA.md) v2를 DB에 구현한다. 구버전·충돌·
   확인 전 사실은 자소서용 확정 사실로 승격하지 않는다.
5. **MD 생성과 검토 UI:** 폴더 목차와 활동별 MD를 만들고, 출처 클릭·역할 질문·수정·재생성을
   연결한다. 사용자 수정 후 이전 인용을 자동 상속하지 않는다.
6. **검색·자소서 연결:** 챗봇과 작성기는 MD 전문만 통째로 믿지 않고 승인된 사실 버전과 원본 인용을
   조회한다. 최종 문장마다 사실 ID·출처가 있고 변경 시 갱신 필요가 표시돼야 한다.

첫 번째 실제 완료 장면: **KT 파일 몇 개 업로드 → 활동 후보 확인 → 출처가 달린 KT 활동 MD →
본인 역할 질문에 답변 → 수정된 MD 재생성**. 이 장면을 검증한 뒤 20~30개 폴더와 대용량 자료로
확장한다.
