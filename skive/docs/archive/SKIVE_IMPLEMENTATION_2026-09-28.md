# SKIVE 활동 기억 파이프라인 구현 현황 (2026-09-28)

이 문서는 이번 변경의 구현 범위와 검증 범위를 구분한다. 기존 `PROJECT_STATUS.md`, `SKIVE_SUMMARY_DESIGN.md`의 오래된 진행 상태 문장보다 이 문서가 최신이다.

## 1. 파일별 읽기 카드

- `drive_file_read_cards`에 파일 ID·버전, 파서 버전, 추출 구간 수, 위치가 붙은 문장·수치 언급, 읽기 범위와 오류를 저장한다.
- 예전 `ready` 파일은 원본을 다시 다운로드하지 않고 추출 구간에서 순차적으로 보충한다. `unsupported/failed` 파일에도 읽지 못한 이유를 기록한다. 화면의 **읽기 카드** 탭은 대표 항목과 모든 추출 구간의 페이지 이동을 제공한다.
- 숫자 언급은 성과가 아니다. 카드에는 개인의 역할이나 성과를 확정하지 않는다. OCR 없는 스캔 PDF, 이미지·영상, 크기 제한 초과 파일은 여전히 읽지 못한다.

## 2. 활동 후보와 합치기·나누기

- 같은 최상위/그다음 폴더의 파일을 **겹칠 수 있는 후보**로 제안한다. 서로 다른 폴더라도 파일명과 읽힌 원문에 드문 공통 단어가 둘 이상 있으면 별도 후보로 제안한다. 파일이 하나뿐이거나 근거가 약하면 억지로 활동을 만들지 않는다.
- 후보 화면에서 일부 파일만 체크해 새 활동을 만들거나 기존 활동에 묶는다. 활동에서 연결을 해제해도 원본 파일은 남고, 한 파일을 여러 활동에 연결할 수 있다.
- 현재 제안은 폴더 위치와 파일명·첫 원문 구간의 단어 겹침에 의존한다. 의미·시기·인물에 따른 깊은 분류는 아직 없다. 폴더 후보는 최근 5,000개 파일, 원문 단어 비교는 최근 읽힌 500개 파일로 제한한다.

## 3. 사실 후보와 사람의 확인

- 활동 단위 비동기 분석 작업을 DB에 저장한다. 연결된 읽기 완료 파일 중 최대 40개에서 첫·마지막·주석 구간을 골라 모델에 나눠 전달한다.
- 모델에는 원문 줄의 번호만 선택하게 한다. 선택한 줄을 서버가 원문에서 그대로 다시 꺼내 검증한 뒤 `candidate`로 보관하고 출처 파일·버전·구간·위치를 붙인다. 모델이 중요한 목표·결과 줄이나 특정 파일을 놓치면, 명확한 원문 줄을 보수적인 검토 후보로 보충한다. 모델이 `user`라고 추정해도 본인 역할로 자동 확정하지 않는다.
- 화면에서 프로젝트/팀/본인 주체, 확인 메모를 입력해 확인하거나 제외한다. 본인 역할로 확인할 때 메모가 필요하다. 결과 수치의 조건·역할, 비슷한 문장의 다른 수치는 질문으로 표시한다.
- 합성 보고서에 실제 모델을 호출해 원문과 일치하는 줄 1개를 후보로 받은 것까지 확인했다. 실제 사용자 자료의 모델 출력 품질은 아직 검증하지 않았다. 내용 전체를 읽는 단계가 아니며, 숫자 충돌 탐지는 같은 문장 형태의 단순 비교다. 따라서 중요한 중간 구간의 사실이나 의미상 충돌을 놓칠 수 있다.

## 4. 활동 요약 MD

- 확인된 현재 사실만 배경·목표·행동·결과·역량·배운 점의 MD 본문에 넣는다. 파일명·버전·구간·원문과 사용자 메모를 함께 표시한다.
- DB에 MD 버전을 저장하고 파일 연결·추출 시각·확인 내용이 바뀌면 **갱신 필요**를 계산한다. 바뀐 출처의 사실은 본문에서 제외하고 재검토 대상으로 표시한다.
- 검토 대기 후보와 질문은 별도 영역에 표시한다. 빈 항목은 추측으로 채우지 않는다.

## 4.1 프로젝트 루트 통합 요약 MD

- 사용자가 `건설장비 이상탐지` 같은 **프로젝트 최상위 폴더**에서 `프로젝트 통합 요약`을 실행한다. 하위 폴더마다 별도 요약을 만들지 않고, 선택한 루트와 모든 하위 폴더를 `drive_project_summaries`의 보고서 하나로 저장한다.
- 프로젝트 아래에 작성자 이름처럼 하위 폴더가 하나만 이어지는 경우 이를 작업 단계로 오인하지 않는다. 처음으로 여러 폴더가 갈라지는 깊이를 찾아 `전처리 → 특징 선택 → 모델링·평가` 같은 실제 단계를 표에 표시한다. 에이전트가 설명하지 못한 단계도 숨기지 않고 `자료 역할 미확인`으로 남긴다.
- 보고서 앞부분은 프로젝트 한눈에 보기, 유형·기간·데이터, 단계 표, 전체 흐름, 목표, 프로젝트·팀 작업, 확인된 본인 작업, 역할 질문, 방법, 의사결정, 수치, 시행착오, 자료 연결, 읽기 범위, 출처의 **고정 목차**를 사용한다. 뒤에는 에이전트가 프로젝트별 연결·도메인 설명·해석·남은 문제를 길게 기록할 수 있는 **AI 확장 부록**을 둔다.
- 에이전트는 프로젝트 범위 안에서만 파일 목록·원문 검색·원문 읽기 도구를 사용한다. 각 주장의 S번호와 수치는 서버가 원문과 다시 대조하고, 에이전트가 인용문을 바꾸어 썼으면 실제 원문 줄로 교정한다. 본인 역할·본인 성과는 자료만으로 자동 확정하지 않고 질문으로 남긴다.
- 일반 챗봇과 자소서 검색은 일치하는 통합 요약 MD를 원본 구간보다 먼저 전달하고, 필요한 원본 구간도 함께 전달한다. 따라서 작은 모델은 먼저 전체 프로젝트 구조를 읽고 세부 근거가 필요할 때 원문을 볼 수 있다.
- 새 분석이 실패해도 이미 만들어진 정상 보고서는 유지한다. 화면에는 기존 보고서와 최근 재분석 오류를 같이 표시하며, `다시 분석`은 자료가 바뀌지 않았어도 실제로 새 작업을 대기열에 넣는다.

## 5. 챗봇·자소서 연결

- 일반 챗봇과 공고별 자소서 대화가 계정의 **현재 출처를 가진 확인된 활동 사실**을 검색한다. 다른 계정, 삭제·변경된 파일, 아직 확인하지 않은 후보는 검색 결과에서 제외한다.
- 활동 사실과 원문 파일, 본인 진술, 이전 자소서를 서로 다른 범주로 전달한다. 답변·초안에서는 `[활동 사실 N]` 인용을 요청하며, 화면에서 연결된 원문을 열 수 있다.
- 숫자와 인용 번호에 대한 기본 검사만 있다. 문장별 주장 지지 여부 전체, 다른 문장의 영향 전파, 과거 초안의 자동 재검토는 아직 없다. 집에서 실제 20~30개 자료로 처음부터 끝까지 검증해야 한다.

## 검증 기록

- SQL 마이그레이션 `0013`~`0015`를 현재 Supabase에 적용했다.
- 프로젝트 통합 요약용 SQL 마이그레이션 `0016`도 현재 Supabase에 적용했다.
- 기존 파일 보충을 마쳤다. 현재 삭제되지 않은 파일 1,079개 중 텍스트 추출 완료 766개, 읽기 미지원 313개에 해당하는 읽기 카드가 모두 있고 누락은 0개다. 미지원 카드에는 실패 이유가 남는다.
- 전체 테스트 85개 통과, 1개 건너뜀. 임시 Auth 두 계정의 API·RLS 테스트에서 사실 확인, 출처 변경 차단, MD 갱신 필요, 활동 사실 검색 격리를 확인했다.
- 파일 읽기 카드와 활동 후보→파일 선택·분리→사실 확인→MD 생성→원본 변경 경고의 Edge 화면을 임시 계정·합성 문서로 확인했다. 챗봇·자소서의 확인된 사실 전달은 합성 문서와 모의 모델 답변으로 검증했다. 실제 사용자 자료의 모델 분석 품질은 별도 확인 항목이다.
- 화력발전소 폴더 54개·파일 369개로 첫 프로젝트 통합 요약을 실행했다. 이 중 텍스트 추출 완료는 119개, 미지원은 250개였다. 첫 결과는 원문 근거 1개만 검증을 통과해 품질이 부족했다. 단계 탐지와 원문 인용 교정을 고친 뒤 다시 실행했으나 OpenAI 조직의 사용량·결제 한도에서 호출이 차단됐다. 현재 DB에는 이전 보고서를 보존한 채 실제 단계 4개가 표시되고, 새 v2 의미 분석은 API 한도가 풀린 뒤 재실행해야 한다.

## 집에서 검증할 순서

현재 서버는 이 PC의 `http://localhost:8010/`에서 실행된다. 집 노트북의 `localhost`는 다른 컴퓨터이므로, 집에서 직접 시험하려면 변경된 코드를 그 노트북에 동기화해 서버와 작업자를 실행하거나 HTTPS로 배포해야 한다. DB와 Storage는 같은 Supabase 프로젝트를 사용할 수 있다.

1. 각자 계정으로 로그인하고 20~30개 파일이 든 폴더를 업로드한다. 업로드 수와 읽기 카드의 `ready/unsupported/failed` 수를 맞춘다.
2. 대표 PDF·PPT·XLSX의 문장·수치·주석 위치를 원본과 대조한다.
3. 활동 후보를 합치거나 나눠 실제 프로젝트 단위로 만든다. 파일이 잘못 묶이지 않았는지 본다.
4. 활동 분석을 시작하고 후보·역할 질문·수치 충돌을 검토한다. 확인된 사실만 MD 본문에 들어가는지 본다.
5. 원본을 다시 읽어 MD의 갱신 필요 표시를 보고, 챗봇과 공고별 자소서에서 그 사실의 주체와 출처가 유지되는지 확인한다.
6. 실제 프로젝트 최상위 폴더에서 통합 요약을 만들고, 하위 단계가 한 보고서에 연결되는지와 AI 확장 부록이 프로젝트 고유 맥락을 충분히 설명하는지 확인한다.
