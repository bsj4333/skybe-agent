# SKIVE 구현·사용 흐름 점검 (2026-09-23)

## 결론

현재는 **근거를 붙여 경험을 저장하고 일부 질문에 답하는 1인 로컬 시제품**이다. 목표인 여러 사용자용 개인 드라이브와 정확한 생애 기억, 공고별 자소서 작성 서비스까지는 계정별 소유권, 대용량 비동기 수집, 파일별 처리 상태, 출처가 유지되는 기억 모델, 답변 검증이 더 필요하다. 특히 현 데이터의 샘플 작성자와 현재 프로필 이름이 다른데도 `my_role_verified=true`인 샘플에서 "제가 진행한" 자소서가 생성됐다. 이 상태로 다른 사용자에게 공개하면 안 된다.

이 문서는 `PROJECT_STATUS.md`, 두 `SKIVE_NEXT_PLAN*.md`, `SCHEMA.md`, 서버·저장소·분석·검색·작성·UI 코드, 샘플 자료, 사용자가 제공한 8유형 질문표를 대조하고 로컬 서버에 실제 요청을 보내 작성했다. 브라우저 제어 수단이 없는 세션이라 **화면을 눈으로 클릭하거나 반응형 레이아웃을 검증하지는 못했다.** `GET /` 200과 응답 HTML이 `ui_mockup/skive_ui.html`과 일치하는 것까지 확인했다.

회귀 테스트는 처음에 pytest 임시 디렉터리 권한 오류가 났다. 작업공간 안의 임시 디렉터리를 지정해 다시 실행한 결과 **47 passed, 1 skipped**다. 이 테스트는 실제 챗봇 답변 품질이나 긴 공고 실행 시간을 증명하지 않는다.

사용자가 제공한 8유형 질문표 기준으로 이번 실측 범위는 다음과 같다. 단순 기억은 95→99 질문 첫 답이 틀렸고, 여러 경험 통합은 실행하지 않았다. 세부 경험은 원문 지정 재질문에서 맞았다. 잘못된 기억·업데이트는 이번에 정정 확정까지 실행하지 않았다. 과거 공부는 없는 SCM 기록에 대한 추측 회피만 확인했다. 공고 분석·경험 매칭·자소서 전체 생성은 `/api/jobs`가 끝나지 않아 결과 검증에 실패했다. 작성기 단독은 역할 미확인 시 빈 초안, 검증 상태 샘플 시 초안 생성을 확인했다. 따라서 8유형 전체를 통과했다고 해석하면 안 된다.

테스트 중 만든 경험 ID는 평가용이다. 점검 후 해당 ID의 로컬 원본 4개·파생 경험·Supabase 청크 7행과 pytest 임시 디렉터리를 정리했다. 채팅 체크포인터에 남은 평가 세션은 전체 회상 자료나 경험 목록에 들어가지 않는다.

`PROJECT_STATUS.md`의 일부 서술은 최신 코드와 어긋난다. 3.1에는 300개 상한이라는 설명이 남아 있으나 코드는 기본 2,000개다. P0 표에서 checkpointer는 완료로 표시됐지만 바로 뒤 문장에서는 미완료처럼 적혀 있다. `SCHEMA.md`의 사실 상태 v2와 실제 SQL 마이그레이션도 동기화되지 않았다.

## 가장 위험한 정확성·보안 문제

1. **신원 연결 오류:** 현재 `data/user.json` 이름은 변성준, `samples/heat_treatment_raw/README.md` 작성자는 김민수다. 그런데 `data/store/heat_treatment_raw/metadata.json`의 `my_role_verified=true`를 작성기가 현재 사용자에게 그대로 적용해 "제가 진행한 개인 프로젝트" 초안을 만들었다. 데이터 소유자와 원문 속 행위자를 별도 ID로 기록하고, 이전 샘플은 격리해야 한다. 과거 이름으로 검증한 사실을 현재 사용자 소유로 자동 이관하지 않는다.
2. **인증·권한 없음:** 모든 `/api/*`가 같은 플랫파일을 읽고, 채팅 세션 ID도 계정에 묶이지 않는다. `RequestContext`의 경험 범위는 사용자 간 접근 제어가 아니다.
3. **업로드 ID 경로 검증 없음:** 개별 파일 상대경로는 검사하지만, 요청의 `id`를 `data/uploads/<id>`와 `data/store/<id>`에 바로 붙이고 기존 디렉터리를 재귀 삭제한다. 외부 접속 전에 서버 발급 UUID, 경로 루트 확인, 이름 별도 저장, 개발용 `/api/experiences` 로컬 경로 엔드포인트 제거가 필요하다. URL 가져오기 SSRF와 UI의 인라인 `innerHTML`/`attrEsc` 문제도 같은 공개 전 단계에서 처리한다.
4. **질문 답변의 검증이 작성기만큼 강하지 않음:** 채팅은 검색 문맥을 넣고 도구를 선택하지만 답변 문장마다 출처·주체·숫자 일치 검사를 하지 않는다. 그래서 95→99퍼센타일을 모델 전환으로 잘못 답하고, 역할 미확인 경험을 강점 소재로 단정했다.
5. **공고 계획의 빈 매칭 폴백:** `apply.py`는 문항에 연결 경험이 없으면 중요도 상위 경험으로 채운다. 관련 근거가 없을 때는 빈 목록과 확인 질문이 남아야 한다.

## 큰 파일과 Supabase의 권장 데이터 흐름

현재 경로는 브라우저→FastAPI multipart→로컬 `data/uploads`→전체 폴더 1회 LLM 분석→로컬 `facts.json`/`experience.md`→DB 청크다. `upload_experience()`는 파일을 `await f.read()`로 통째로 메모리에 올리고, `loaders.py`는 **2,000,000바이트 초과 파일을 이유 표시 없이 분석에서 제외**한다. DOCX/HWP/HWPX/이미지 OCR/JSX 등도 경험 분석 로더에 없다. CSV는 20행·2,000자 미리보기만 써서 뒤쪽 결과 수치를 놓칠 수 있다. `analyzer.py`는 폴더 텍스트 320,000자 초과 시 실패하며, 그 아래라도 한 번의 모델 문맥에 의존한다.

목표 흐름:

```text
브라우저 폴더 선택 → 파일별 업로드 세션(TUS 재개/진행률) → 비공개 Supabase Storage 원본
  → files/folders DB 메타데이터(사용자·경로·크기·해시·버전·처리 상태)
  → 지속 가능한 작업 큐(run_id, 단계·재시도·취소)
  → 파일별 파싱/OCR·누락 사유 기록 → 원본 위치를 가진 청크 → 숫자·사건·역할 사실 후보
  → 중복/충돌/출처 검증 → 사용자 확인 → 구조화 사실 DB
  → 출처를 붙인 experience.md/프로필/검색 색인(버전 있는 파생물)
  → 공고별 근거 선택 → 문장별 사실 ID를 가진 자소서 → 대화형 수정
```

- **원본 바이트:** 비공개 Storage 버킷의 객체로 보관. Storage 내부의 `storage.objects`는 파일 메타데이터이고 실제 바이트는 객체 저장소에 있다. 앱의 `files` 테이블에는 `user_id`, `folder_id`, `storage_key`, 원래 이름/상대경로, MIME, 크기, SHA-256, 버전, 업로드/파싱/색인 상태를 둔다. 파일을 DB `bytea`나 청크 테이블에 통째로 넣지 않는다.
- **큰 파일 업로드:** Supabase는 6MB 초과나 불안정한 네트워크에 TUS 재개 업로드를 권장한다. 파일별 전송·재개·체크섬을 분리하고 폴더는 경로를 가진 파일들의 manifest로 표현한다. 2,000개를 한 HTTP 요청에 묶지 않는다. 필요하면 서버가 짧은 수명의 업로드 URL을 발급한다. [Resumable Uploads](https://supabase.com/docs/guides/storage/uploads/resumable-uploads)
- **권한:** Auth 사용자 UUID를 모든 폴더·파일·경험·사실·청크·공고·결과물에 연결한다. Storage와 DB 모두 RLS 및 서버 권한 검사를 적용하고 두 계정 교차 접근을 자동 테스트한다. 서비스 키는 RLS를 우회하므로 일반 사용자 조회 경로에서 무조건 쓰면 안 된다. [Storage Access Control](https://supabase.com/docs/guides/storage/security/access-control), [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)
- **처리:** 업로드 성공과 분석 성공을 분리한다. 파일마다 `uploaded / parsing / parsed / unsupported / failed` 및 이유를 보여주고, 청크·사실·요약은 동일 `file_version`을 가리키게 한다. 재시도는 완료 단계부터 하고, 원본 교체는 새 버전으로 기록한다. 수치가 많은 CSV는 미리보기와 별도로 스키마·통계·선택한 결과 행을 구조적으로 추출한다.

## MD 요약과 자소서의 관계

`experience.md`는 사람이 확인하고 챗봇이 회상할 수 있는 **읽기용 파생물**이다. 현재 `writer.build_bundle()`은 MD 파일 자체보다 `facts.json`의 본인·팀·본인 진술·결과 구분을 직접 읽는다. 이 방향이 맞다. MD만 유일한 기억으로 삼으면 인용 위치, 주체, 숫자, 정정 버전이 사라진다.

요약 MD에는 한눈에 보는 STAR, 시간·내 역할·판단·행동·정량 결과, 확인이 필요한 질문, 원본 링크를 넣되 각 문장/항목은 `fact_id`·`file_id`·원본 위치·검증 상태를 가리켜야 한다. 자소서 문항에는 공고 요건에 맞는 **사실 후보 2~3개와 선택 이유/부족한 근거**를 먼저 제시하고, 확인된 사실로만 초안을 쓴다. 초안의 문장마다 근거 ID를 저장해 수정·철회 시 stale 표시 및 재검증을 한다. 소재 추천도 동일한 후보 선택기를 써야 채팅이 역할 미확인 팀 성과를 내 강점으로 바꾸지 않는다.

## 권장 작업 순서와 완료 기준

1. **현재 데이터 격리와 신원 수리:** 샘플/실사용 데이터를 분리, 과거 `my_role_verified`를 사용자 ID와 대조해 재검토. 테스트 ID 정리. 완료 기준: 다른 사람 원본으로 "제가" 문장 0건.
2. **공개 전 경계:** 인증, 계정별 DB·Storage 권한, 서버 발급 ID, 경로·URL·HTML 입력 검증. 완료 기준: 두 사용자 간 목록/다운로드/검색/세션/자소서 교차 접근 0건.
3. **파일을 드라이브의 기본 객체로:** 임의 폴더와 파일을 먼저 저장·탐색·다운로드하게 하고 경험 분석은 선택 작업으로 둔다. 파일별 누락/오류와 원본 버전을 보여준다. 완료 기준: 큰 폴더 업로드가 끊겨도 재개되고 분석 실패가 원본 업로드를 취소하지 않음.
4. **비동기 분석과 기억 모델:** 작업 큐, 파일별 파싱, 분할 추출·통합, 숫자 검증, 소유자 확인, 출처·버전·stale 전파. 완료 기준: 300개 이상 혼합 폴더에서 누락 파일 0개로 표시하거나 사유 기록, 원본 위치로 역추적 가능.
5. **질문·소재·자소서 평가셋:** 사용자가 첨부한 8유형 표를 `expected_file_id / fact_id / answer_or_abstain / owner / numeric_exactness`로 만든다. 첫 오답(95→Autoencoder), 신원 혼동, 없는 SCM 기록, 유사 문항 중복을 필수 회귀 사례로 둔다. 완료 기준: 출처·주체·수치 오류 0건인 holdout을 통과하고 전체 공고 작업이 제한 시간 내 상태를 보여주며 완료.

DeepAgents 전면 이전은 이 문제들을 해결하지 않는다. 현재 계획대로 FastAPI·LangGraph를 유지하면서 영속 작업 상태, 권한 검사, 실행 예산, 출처 있는 기억을 먼저 완성하는 것이 타당하다.
