# 설계: 사용자 작업별 모델·실행 방식 배치

> 작성: Claude (2026-09-29) · 상태: **spec — 사람 승인 필요** · 관련 항목: F-106, F-205, F-206

## 1. 목적

지금은 작업별로 어떤 모델을 어떻게 쓸지 정해진 기준이 없다. 그래서 두 가지 문제가 생겼다.

- **비용 사고:** `skive/drive_project_summary.py`의 기본 모델이 코드에 `gpt-6-astra`로 박혀 있다(`DEFAULT_MODEL`). 환경변수를 안 주면 가장 비싼 모델이 돈다. 선불 크레딧 소진(2026-09-28)과 "실수로 astra를 썼다"는 경험이 이 경로와 맞물린다.
- **품질 판단 혼동:** "Agents API가 성능이 좋다"는 인상은 2026-09-28 비교 한 번에서 나왔다. 그런데 그 비교는 모델(4o-mini vs astra)과 검색 횟수(1회 vs 9회)를 **동시에** 바꿨다. 같은 원문만 주면 4o-mini도 수치 6개를 전부 맞혔다(3.1초). 성능 차이의 큰 원인은 모델이 아니라 **다시 검색하는 루프**일 가능성이 높다.

## 2. 핵심 원칙: 세 가지를 따로 정한다

"에이전트냐 아니냐"와 "비싼 모델이냐 아니냐"는 별개의 결정이다.

| 축 | 선택지 | 결정 기준 |
|---|---|---|
| **작업 방식** | 워크플로(정해진 순서) / 에이전트(모델이 도구를 골라 반복) | 다음 단계가 입력에 따라 달라지는가? 다시 찾아보거나 사용자에게 되묻는 판단이 필요한가? |
| **모델 등급** | T0 없음 / T1 저가 / T2 중간 / T3 최상위 | 틀렸을 때의 피해, 추론 난이도, 호출 빈도 |
| **실행 기반** | 자체 루프(LangChain `bind_tools`, 현재 `drive_orchestrator.py`) / OpenAI Agents API(`beta.agents.sessions`) | 계정 범위 강제, 비용 상한, 테스트 가능성, 모델 교체 쉬움 |

**에이전트가 곧 비싼 모델은 아니다.** 저가 모델로도 도구 루프는 돌릴 수 있다. 비싼 모델은 저가·중간 모델로 평가셋 기준을 못 넘는 작업에만 쓴다.

| **공고 분석** | 워크플로 | T1 | 자체 | 공고 텍스트에서 요구사항을 구조화하는 단발 작업 |

### 공부할 때도 에이전트여야 하나?

**가벼운 에이전트면 충분하다.** 공부 질문은 두 종류다.

- **"내 자료에서 이 개념 어디 나왔지?"** → 내 자료 검색이 필요하다. 검색 도구를 가진 에이전트.
- **"PCA가 뭐야?"** → 일반 설명이다. 근거 검증 없이 T1이 바로 답해도 된다. 단, 이 답을 **내 경험 기록으로 저장하지 않는다**(`derived`).

그래서 T1 모델에 "내 자료 검색" 도구 하나를 주고, 모델이 필요할 때만 부르게 한다. 복잡한 다단계 계획은 필요 없다.

## 6. 자체 루프 vs OpenAI Agents API: 실험으로 결정

지금 근거로는 어느 쪽이 나은지 알 수 없다. 기본값은 **자체 루프**를 제안한다.

- 계정 범위(RLS) 도구를 우리가 직접 통제한다.
- 모델을 바꾸기 쉽고, 가짜 모델로 테스트할 수 있다.
- 비용·시간 상한을 우리가 건다.

Agents API는 아래 실험에서 **같은 모델 기준으로** 확실히 나을 때만 해당 작업에 쓴다. F-105(크레딧 충전) 이후, 평가셋 v0(F-201)으로 진행한다.

| 조건 | 실행 기반 | 모델 | 재검색 |
|---|---|---|---|
| A (현재) | 자체 | 4o-mini | 1회 |
| B | 자체 | 4o-mini | 최대 3회 |
| C | 자체 | T2 | 최대 3회 |
| D | Agents API | T2 | 모델이 결정 |

측정: 정답률, 근거 Recall@5, 소요 시간, 비용. **한 번에 한 가지만 바꿔 비교한다.** B가 A보다 크게 좋으면 병목은 검색이고, C가 B보다 좋으면 모델, D가 C보다 좋으면 실행 기반이다.

## 8. 불변조건 영향
