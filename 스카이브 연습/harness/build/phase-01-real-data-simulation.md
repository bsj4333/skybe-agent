# phase-01: 실자료 시뮬레이션

> 작성: Claude · 상태: ready (phase-00 이후 시작) · 관련 항목: 시뮬 중 생기는 bug 항목 전부

## 1. 목적

지금까지의 검증은 대부분 합성 자료와 임시 계정으로 했다. 사람이 자기 실제 프로젝트 자료를 넣고 데모 장면대로 써보면서, 이해·기억·활용 계층의 결함을 찾아 `feature_list.json`에 쌓는다. 이 단계의 산출물은 코드가 아니라 **재현 가능한 결함 목록**과 **평가셋 후보**다.

## 2. 한 번의 시뮬 사이클

```
사람: 시나리오 실행 (화면)
  → Claude: 관찰 (API 응답·로그·읽기 전용 SQL) + 결함 기록 (bug, 재현 절차)
  → Claude: 심각도 분류, 작은 버그는 ready / 큰 문제는 설계 문서
  → Codex: ready 항목 수정 (한 번에 최대 3개) → review
  → Claude: 검토 → passing 또는 changes_requested
  → 사람: 수정된 부분을 같은 시나리오로 다시 확인
  → 다음 사이클
```

사이클 하나에 결함을 너무 많이 쌓지 않는다. P0가 나오면 그 사이클은 거기서 멈추고 P0부터 고친다.

## 3. 시나리오

사용자가 제공한 8유형 질문표와 데모 장면을 합친 것이다. 각 시나리오는 **실제 프로젝트 2개 이상**(예: 화력발전소 이상탐지, KT)으로 돌린다.

| ID | 시나리오 | 사람이 하는 것 | 확인할 것 |
|---|---|---|---|
| S1 | 업로드·읽기 범위 | 프로젝트 폴더 업로드 | 파일 수, `ready/unsupported/failed` 개수, 폴더 구조·이름이 원본 그대로인지, 대표 PDF·PPT·XLSX 원문 위치가 맞는지 |
| S2 | 활동 묶기 | 활동 후보를 합치고 나눠 실제 프로젝트 단위로 | 엉뚱한 파일이 섞이지 않는지, 빠진 파일은 없는지 |
| S3 | 사실 확인 → 활동 MD | 사실 후보 확인·제외, 역할 질문에 답하기 | 확인한 사실만 MD 본문에 들어가는지, 본인/팀 구분, 수치가 원문과 같은지 |
| S4 | 단순 기억 | "그때 임계값 95퍼센타일에서 뭐로 바꿨지?" 같은 세부 질문 | 정답, 근거 파일·위치, 모르면 모른다고 하는지 |
| S5 | 여러 경험 통합 | "내 데이터 분석 경험 전체에서 강점이 뭐야?" | 여러 활동을 근거와 함께 묶는지, 역할 미확인 경험을 본인 역량처럼 말하지 않는지 |
| S6 | 잘못된 기억·정정 | 틀린 수치를 말하며 질문 → 정정 → 새 대화에서 재질문 | 틀린 전제를 바로잡는지, 정정 뒤 옛 사실이 다시 나오지 않는지 |
| S7 | 과거 공부 | 자료에 없는 수업 내용 질문 | 추측으로 지어내지 않는지 |
| S8 | 공고 분석·매칭·자소서 | 실제 공고와 문항 입력 → 초안 → 수정 요청 | 문항별 경험 매칭, 문장마다 근거, 팀 성과를 본인 성과로 쓰지 않는지, 분량 |

## 4. 결함 기록 양식

`feature_list.json`에 아래 필드로 추가한다. 사람은 채팅으로 말하기만 하면 Claude가 기록한다.

```json
{
  "id": "B-0xx",
  "type": "bug",
  "severity": "P0",
  "scenario": "S6",
  "title": "정정한 F1 수치가 새 대화에서 옛 값으로 나온다",
  "repro": ["계정 A로 로그인", "활동 X에서 F1 0.82를 0.80으로 정정", "새 대화에서 'F1 몇이었지?' 질문"],
  "expected": "0.80과 정정 출처를 답한다",
  "actual": "0.82라고 답한다",
  "observed": "2026-10-xx, 서버 로그 요약 또는 SQL 결과 요약",
  "status": "failing"
}
```

## 5. 심각도

| 등급 | 기준 | 처리 |
|---|---|---|
| P0 | 핵심 약속 위반: 다른 계정 자료 노출, 팀→본인 오귀속, 원문에 없는 수치, 정정 뒤 옛 사실 재등장 | 즉시. 다른 작업 중단 |
| P1 | 사용이 막힘: 업로드 실패, 무한 대기, 오류 화면 | 이번 사이클 안에 |
| P2 | 품질 부족: 검색 누락, 요약 빈약, 느림 | 모아서 phase-02 설계에 반영 |
| P3 | 개선 아이디어 | `idea`로 기록만 |

## 6. 관찰 규칙

- 사람 계정의 DB는 **SELECT만** 한다. 확인용 쓰기가 필요하면 임시 계정에서 재현한다.
- 유료 모델을 부르는 재분석은 폴더 단위로 한 번씩만, 여러 폴더 일괄 재분석은 먼저 비용을 묻는다.
- 시뮬 1회가 끝나면 Claude가 `harness/reviews/YYYY-MM-DD-sim-주제.md`에 요약한다: 돌린 시나리오, 결과 표, 새 결함 ID, 평가셋 후보.

## 7. 완료 조건

- [ ] (real_data) S1~S8을 실제 프로젝트 2개 이상에서 각각 1회 이상 실행
- [ ] (real_data) 열린 P0 결함 0건
- [ ] P1 결함은 수정 완료 또는 미루는 이유를 기록
- [ ] 실패한 질문과 기대 답이 평가셋 후보로 20건 이상 모임 (phase-02의 입력)

## 8. 반복 제한

- 사이클당 Codex 수정은 최대 3개 항목.
- 같은 결함이 수정 후에도 2번 재발하면 설계 문서를 따로 쓴다(땜질 중단).
- 한 사이클이 모델 비용 $2를 넘을 것 같으면 먼저 사람에게 묻는다.
